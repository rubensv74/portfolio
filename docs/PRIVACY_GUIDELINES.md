# Privacidad y confidencialidad

## Objetivo

El portfolio es público. Todo contenido debe revisarse pensando no solo en lo que queremos enseñar, sino también en lo que no debemos revelar.

## Regla principal

**Todo dato, nombre, identificador, hito, documento, valor y ejemplo visible en el portfolio público será ficticio cuando derive de un entorno profesional real.**

No basta con sustituir el nombre del proyecto o alterar una cifra. Una recreación segura debe evitar también combinaciones de terminología, códigos, hitos, controles, documentos o estructuras que permitan reconstruir cómo funciona realmente un entorno corporativo.

El portfolio mostrará problemas, decisiones, métodos y capacidades profesionales, pero no reutilizará información operativa real ni reproducirá fielmente estructuras internas innecesarias.

Los nombres de los propios productos o iniciativas de Rubén podrán mantenerse únicamente cuando se haya decidido presentarlos públicamente y el nombre no revele información confidencial.

## Qué debe ser ficticio

Se crearán expresamente para el portfolio:

- nombres de proyectos mostrados dentro de las soluciones;
- empresas, clientes, contratistas y proveedores;
- personas y responsables;
- ubicaciones y áreas internas;
- códigos e identificadores;
- correos, usuarios y referencias documentales;
- fechas operativas;
- cantidades, estados y volúmenes de trabajo;
- valores económicos;
- datos de tablas y gráficos;
- textos descriptivos que puedan proceder de registros reales;
- ejemplos de incidencias, tareas, riesgos, activos u órdenes;
- nombres de hitos y eventos cuando procedan del proceso corporativo real;
- códigos de procedimientos, auditorías, controles, formularios o informes;
- nombres de documentos y archivos;
- indicadores y reglas de validación cuando reproduzcan controles internos;
- cualquier otro dato utilizado para poblar una recreación.

## Terminología y estructura

Los términos estándar del sector pueden utilizarse cuando sean necesarios para explicar una capacidad profesional —por ejemplo, RCM, AMEF, SQL, Power BI o conceptos genéricos de gestión de proyectos—.

En cambio, se sustituirá o generalizará cualquier terminología que revele:

- nombres internos de procesos, estados o etapas;
- hitos específicos utilizados por la organización;
- nombres de pantallas, módulos o flujos internos;
- códigos de controles o procedimientos;
- nomenclaturas particulares de bases de datos, documentos o informes;
- estructuras que permitan deducir el funcionamiento detallado de un sistema interno.

Cuando exista duda entre conservar un término real o usar una variante ficticia/genérica, se utilizará la variante ficticia o genérica.

## Información que no debe aparecer

No publicar:

- nombres reales de clientes, empresas, proyectos internos, contratistas o proveedores;
- datos personales;
- correos electrónicos internos;
- nombres de compañeros asociados a información de trabajo;
- credenciales, claves, tokens o secretos;
- direcciones internas de servidores o servicios;
- cadenas de conexión;
- capturas con información confidencial;
- datos reales de negocio;
- documentos internos completos o fragmentos reconocibles;
- código que contenga información sensible;
- nombres de tablas, procedimientos, endpoints, rutas o servicios internos cuando no sean necesarios;
- detalles de seguridad que puedan facilitar un acceso no autorizado.

## Proyectos realizados en un entorno profesional

Podrán utilizarse como casos de estudio siempre que se cuenten de forma segura.

Podemos explicar el contexto general, el problema, el papel desempeñado, las decisiones y el aprendizaje. Para demostrar visualmente la solución se utilizarán recreaciones construidas específicamente para el portfolio.

### Simplificar

Explicar el problema y la solución sin revelar detalles internos que no aportan valor al portfolio.

### Recrear

Crear nuevas pantallas, diagramas o prototipos que representen la idea sin copiar fielmente pantallas, nombres, estructuras o información operativa real.

### Desacoplar

Una recreación debe cambiar varias dimensiones a la vez: nombres, códigos, hitos, fechas, cifras, textos, documentos y, cuando sea necesario, la propia estructura visual o terminología.

### Usar datos ficticios

Todos los conjuntos de datos utilizados para enseñar pantallas, informes, tablas, gráficos o ejemplos serán ficticios.

No basta con cambiar un nombre dentro de una captura real. Cuando una pantalla contenga información de trabajo, la opción preferida será reconstruirla desde cero.

## Capturas de pantalla

Las capturas reales de aplicaciones profesionales **no se utilizarán como material público**.

Podrán servir como referencia privada para entender una función o recrear una idea, pero la versión publicada se construirá de nuevo con información ficticia y una estructura suficientemente desacoplada del original.

## Métricas y resultados

Los datos ficticios pueden utilizarse para explicar cómo funciona una pantalla, pero nunca para fingir resultados del proyecto.

No se inventarán porcentajes de mejora, ahorro, reducción de errores, retorno económico u otras métricas de impacto.

Solo se publicarán resultados cuantitativos cuando exista evidencia verificable y sea seguro divulgarlos. En caso contrario se describirá el resultado de forma cualitativa.

## Arquitectura y detalles técnicos

Los diagramas públicos deben enseñar la idea de la solución, no convertirse en un mapa detallado de sistemas internos.

Los nombres de servidores, bases de datos, esquemas, tablas, procedimientos, entornos, flujos, rutas, APIs y sistemas internos se sustituirán por denominaciones ficticias o genéricas.

Las relaciones técnicas también se simplificarán si su nivel de detalle pudiera revelar arquitectura interna innecesaria.

Cuando un detalle técnico no sea necesario para demostrar una capacidad profesional, se omitirá.

## Uso de inteligencia artificial

No se introducirán datos confidenciales en herramientas de IA con el propósito de crear contenido para el portfolio.

Las recreaciones se construirán utilizando únicamente información segura y datos ficticios creados expresamente para este proyecto.

## Revisión obligatoria antes de publicar un proyecto

Cada caso de estudio deberá superar estas preguntas:

1. ¿Todos los datos visibles han sido creados expresamente para el portfolio?
2. ¿Todos los nombres de proyectos, empresas, personas y ubicaciones de ejemplo son ficticios?
3. ¿Los hitos, códigos, documentos, controles e indicadores son ficticios cuando proceden de un entorno profesional?
4. ¿Se ha reutilizado accidentalmente algún identificador, texto, cifra, fecha o nombre de producción?
5. ¿La terminología revela nomenclaturas o procesos internos innecesarios?
6. ¿Una recreación reproduce demasiado fielmente la estructura de una pantalla o sistema real?
7. ¿Un diagrama revela arquitectura, tablas, procedimientos, rutas o servicios internos?
8. ¿Las métricas presentadas como resultados son verificables y publicables?
9. ¿La combinación de varios datos ficticios podría permitir identificar un proyecto real?
10. ¿Podemos demostrar la misma capacidad con menos información?

Si alguna respuesta plantea dudas, el contenido no se publica.

## Principio final

El objetivo del portfolio es demostrar criterio profesional. Proteger correctamente la información forma parte de ese criterio.
