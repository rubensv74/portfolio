# Guía de contenidos

## Objetivo

Todos los textos del portfolio deben ser fáciles de entender para una persona que no conoce el proyecto ni las herramientas utilizadas.

El portfolio debe sonar profesional, concreto y creíble.

## Regla principal

Primero explicamos el problema y el impacto. Después, si aporta valor, explicamos la tecnología.

Ejemplo:

**Mejor:**

> El equipo necesitaba revisar miles de incidencias de forma más rápida durante las reuniones de seguimiento. Se diseñó una pantalla que concentra los indicadores principales, permite filtrar la información y facilita revisar cada incidencia sin saltar entre varias herramientas.

**Peor:**

> Se creó una Canvas App con componentes reutilizables, Power Automate y procedimientos almacenados.

La segunda explicación puede aparecer después, pero no debe ser la puerta de entrada al proyecto.

## Tono

Los textos deben ser:

- claros;
- naturales;
- concretos;
- profesionales;
- comprensibles sin contexto previo.

Debemos evitar:

- exageraciones;
- palabras de moda sin contenido;
- lenguaje excesivamente técnico;
- frases que parezcan escritas para impresionar;
- afirmaciones que no podamos justificar.

## Cómo contar un proyecto

### El problema

Explicar qué estaba ocurriendo antes de la solución.

### El contexto

Dar solo la información necesaria para entender por qué el problema importaba.

### Mi papel

Diferenciar con claridad qué hizo Rubén, qué se hizo en colaboración y qué dependía de otras personas o equipos.

No atribuirse resultados colectivos como trabajo individual.

### La solución

Contar la idea principal antes de entrar en detalles.

### Las decisiones

Seleccionar las decisiones que demuestren criterio. No documentar cada pequeño cambio.

### El resultado

Priorizar resultados verificables. Si no existen métricas fiables, describir mejoras observables sin inventar cifras.

### Los aprendizajes

Mostrar evolución profesional. Reconocer cambios de criterio o cosas que hoy se abordarían de otra manera puede reforzar la credibilidad.

## Uso de tecnologías

Las tecnologías deben aparecer relacionadas con una necesidad concreta.

Por ejemplo:

- SQL Server para organizar y consultar información;
- Power Apps para construir la experiencia de usuario;
- Power Automate para automatizar procesos;
- Power BI para analizar y comunicar datos;
- GitHub para mantener documentación y cambios ordenados;
- IA para acelerar análisis, documentación, prototipado o desarrollo bajo supervisión.

No es necesario explicar herramientas conocidas si no ayudan a comprender el caso.

## Imágenes y diagramas

Cada elemento visual debe responder a una pregunta.

Una captura de pantalla no debe incluirse simplemente porque sea bonita. Debe ayudar a explicar una función, una decisión o una evolución.

Cuando una imagen real no pueda publicarse, se recreará una versión segura con datos ficticios.

## Extensión

El visitante debe poder entender la idea principal de un proyecto rápidamente y profundizar solo si quiere.

Por eso cada caso deberá tener:

- un resumen breve al principio;
- una lectura completa para quien quiera conocer el proceso.

## Perfil profesional

No debemos encerrar el posicionamiento en una herramienta concreta.

La narrativa debe mostrar una combinación de:

- conocimiento del negocio;
- análisis funcional;
- diseño de soluciones;
- datos y automatización;
- capacidad para aprender y construir;
- uso responsable de inteligencia artificial.

## Regla de revisión

Antes de publicar cualquier texto hay que comprobar:

1. ¿Lo entendería alguien ajeno al proyecto?
2. ¿Explica el valor antes que la herramienta?
3. ¿Es cierto y demostrable?
4. ¿Está claro cuál fue mi papel?
5. ¿Hay información que no debería hacerse pública?
6. ¿Podría decirse de forma más sencilla?
